# 角色、派工和审查模板

## 角色模型

默认按任务复杂度使用 3–5 个角色，可由较少 agent 顺序承担，独立审查不得由对应产出作者承担：

1. **Lead/集成人**：冻结契约和写入权限、安排依赖及资源、核验审查会话与事件、处理门禁和唯一提交；对最终 diff 和交付负责。
2. **实现者**：所属仓库隔离 worktree 中实现、测试、记录版本及风险，不批准自己的代码。
3. **验证/测量者**：维护基线、运行身份、正确性与性能证据，明确失败与未测，不将自己产生的证据当作独立审查。
4. **独立代码/语义审查者**：核对规范、算法、状态、ABI 与覆盖；对阻断项作可复核结论。
5. **独立数据/合规审查者**：核对原始数据、身份、单位、报告/图、布局和证据引用。

首版工具对独立性采用保守限制：本 gate 及全部上游 gate 的 artifact/freeze 作者均不能批准本 gate；`advance` 的推进人不得是本 gate 任一有效审批人。这比仅排除实际受审 scope 作者更严格，可能需要安排额外审查者，不能靠更换名称规避；Lead 仍须核实真实身份和范围。

不同角色可并行，但共享文件、分支、配置、安装前缀及生成器必须串行或隔离；每个共享分支只有一个集成/提交负责人。最多 16 个 agent，优先复用；新建 agent 必须显式选择适合难度的模型，不凭名称假设其独立性。运行环境仅在支持相应工具且已授权时建立任务板、启动 agent 或定时采集。

## 模型选择与有限迭代

模型路由在每次任务开始时从当前授权模型列表确认，随后在所有创建调用显式写 provider/model，不使用隐式默认。本工作区已使用的示例为：材料归纳与常规脚本由 `kxy/deepseek-v4-1-flash-261017`，跨材料审阅/代码方法学复核由 `kxy/gpt-6.1-terra`；它们只是可用路由示例，不保证未来仍存在或自动优于其他模型。数值/ISA 高风险项应由具有对应能力且未参与产出的审查者审阅；换模型不自动构成独立。

Lead 在 G0 契约文件（`contract_sha256` 所引用文件，不是新增 CLI freeze 键）必填 `max_rounds`、每轮候选上限、agent 并发上限、CPU/内存/模拟器时长、审查时间、重试次数、超时和停止条件；不得把空预算解释为无限。每轮固定执行：

1. 读取当前有效契约、状态、未决 bug 与失败清单，选择一个可证伪假设；检查资源及授权，不靠 goal 自动恢复旧运行。
2. 分配不重叠写入范围；Team 中先读取任务并 claim，依赖完成后显式通知下游，任务板不是调度器或文件锁。
3. 实现与功能预检后，收集永久证据；关键阶段先独立批准再扩大规模，命中停止条件立即停止新派工。
4. 审查阻断则记录责任与最小修复，不直接改判；修改输入/源码/数据后生成新版本、使受影响后续审批失效。
5. 正确性、保护场景与最终库态采纳规则全部满足才保留候选；否则回退单项并保留负结果。下一轮必须仍在冻结预算及授权内。
6. 达成目标、预算耗尽、用户停止或缺少必需资源时交接当前已证实结果、失败/未测范围、可继续的最早门禁。不能为了继续自主迭代而降低阈值或伪造批准。

完整开发 CLI 不会自动执行上述 agent 循环；这些是 Lead 的必做操作与审计要求。纯资料归纳可以复用作者作为另一角色，但不得批准其对应产出；关键双审需要额外非作者，不能让作者用不同 reviewer 名补足人数。

## 派工模板

```text
任务/阶段与目标：
基线（仓库、分支、commit、工作区状态）：
作者与审阅者角色、显式模型：
允许写入路径（精确到文件/目录）：
禁止路径与任务顶层白名单：
共享资源、前置依赖、提交责任/权限：
输入与适用配置、预期输出及永久证据入口：
验收 checklist 编号、限制、超时/并发及停止条件：
不得执行的操作（如仿真、删除、推送）：
交接字段：已改范围、结果、当前身份、问题、下一步：
```

任务顶层只允许文件 `plan.md`、`archive.md`、`roadmap.md`、`progress.md`、`idea.md`、`changelog.md`、`ref.md`、`.layout-allow`；目录 `tmp/`、`log/`、`script/`、`data/`、`report/`、`bug/`、`build/`、`build-recipes/`、`worktree/`。其他条目须事先按适用规范声明理由；不得自行扩大写入范围。进度与变更只追加。

## 独立审查模板

```text
门禁与范围：
被审对象：各仓库 commit 与未提交差异身份、配置/构建/数据/报告 hash：
作者与实际执行人：
审查者、角色、独立性说明：
DSH session id 与事件序号范围（可由 Lead 只读核对）：
逐项 checklist 编号：pass/fail/na，原因和证据（这是 review judgement；结果矩阵另用 pass/fail/skip/not_run/not_applicable）：
阻断项、责任人、修复及重测身份：
非阻断限制、未覆盖项：
结论：approve / request_changes / blocked；适用对象和失效条件：
Lead 核验记录：
```

Lead 核对事件实际内容、审查范围及作者关系；一个自填 reviewer 名或事件号不能证明独立性。修复更改受审对象后需复审受影响部分；前次批准不能自动套用到新 hash。

## bug 与误报模板

```text
状态：待确认 / 已确认 / 已撤回 / 已修复待复验 / 已关闭
观察：环境、版本、输入、预期与实际、退出状态：
证据：命令、BIN/工具/emu/ref hash、最小复现、必要日志或波形：
规范/ABI 假设和独立核查：
可证实的现象与未证实的根因假设（分开写）：
交叉验证、影响矩阵和阻断门禁：
修复/撤回理由、复测对象和复审：
```

首先排除测试期望、索引单位、mask/tail 语义、工具链与运行环境问题；现象跨模型复现不自动证明硬件根因。保留有独立定位价值的失败输入与证据；不以 hash 冒充尚未保留的波形。
